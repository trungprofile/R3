# Wave 4b — s1-8-admin

**Status:** complete

**Built:**
- `AdminScreen` — S1.8's four sub-screens (Accounts · Donors · Trucks · Categories) behind `components/Segmented.tsx` in `mode="tabs"` with `tabPanelProps`, exactly one panel mounted at a time (S1.8 Layout, A131).
- `AccountsPanel` + `AccountForm` — the account list, create and edit: first/last name, the auto-generated username shown **read-only** (I3), a single-pick tier row (I1), three independent duty toggles (I2), phone/address (Admin-only edit), and a PIN-or-password field whose kind follows the tier and is never asked about.

- `MasterPanel` + `masters.ts` — donors, trucks and categories as one panel with three configs, each with add / edit / remove and §3.3's "In use ⇄ Archived/Inactive/Deactivated" toggle. Categories ship here per build-plan **D2** and are inert until Phase 2, as expected.
- `logic.ts` — every rule and every sentence this screen can show, pure and tested: the §5.1 username preview, tier/duty controls, the credential plan, what a create and an edit actually send, and the I21 outcome copy.
- `admin.css` — tokens only, `s18-` prefixed, desktop-canonical column that still stacks.

**Invariants:** this lane **enforces nothing** — it is a client screen, and every rule below is enforced again server-side (`architecture.md §4.5`). What it does is render each one in the shape the invariant actually has, cited at the point of use:
- **I1** (tier is a hierarchy) — one pick from an ordered segmented row; `ADMIN` absent when creating, per cap 1. Enforced tier 1 (`app_user.tier` enum) + tier 3 (route `access: { tier: 'ADMIN' }`, `services/user.ts`).
- **I2** (duties are set membership) — three independent toggles; none, any mix, or all three. A duty change is sent as the whole set and compared as a set, never as a list. Enforced tier 1 (`user_duty` PK) + tier 3.
- **I3** (username unique, immutable after creation) — read-only text on both create and edit, never an input; the preview mirrors `domain-modeling.md §5.1` including the collision suffix and counts deactivated handles as taken; the created account's **real** username comes from the response. Immutability is structural: `UpdateUserRequest` has no `username` field, so a patch built from this form cannot carry one. Enforced tier 1 (`uq_user_username`) + tier 3.
- **I21** (soft-delete vs hard-delete) — one Remove, a confirm that names the consequence without predicting the branch, and `RemoveUserResponse.outcome` / `RemoveMasterResponse.outcome` reported in a sentence per entity. The lifecycle toggle is kept visibly distinct from Remove, because it is an ordinary field edit, which I21 always allows. Enforced tier 3 (`*HasHistory()` inside the write transaction).
- **§4.2** credential kind — derived from tier via `credentialKindFor`, never stored and never offered as a choice; a tier change across the PIN/password line makes a new credential required, with the reason on screen.

**Deliberately not done:**
- **No Devices sub-screen.** `GET/POST /devices` exists and is Admin-gated, but S1.8's Layout line names exactly four sub-screens, and `ui-ux-spec.md` S1.5 states the receiver tablet's device registration is itself Phase 2. Consequence to be aware of: **in Phase 1 no screen anywhere registers a shared device**, so the 30-min/12-h shared-device session policy is unreachable through the UI. Reported rather than built — a fifth tab would contradict the one Layout line written for this lane.
- **No Routes sub-screen.** `/routes` (+ `/:id/restore`) is S1.6's route builder and belongs to the `s1-6-schedule` lane; S1.8 has no Routes tab. My brief listed those endpoints under this lane, so I am naming the choice.
- **No reactivate for a deactivated account** — see `Assumed:`; there is no endpoint for it.
- **No single-record re-fetch** (`GET /users/:id`, `GET /donors/:id`, …). The list row already carries the whole record, so a form opens from list data. After every write the list is re-read, so nothing is left optimistic.
- **No search or filter on the four lists.** ~40 accounts and ~15 donors at this deployment, and §1.7 says strip the surface. Add one when a list is long enough to need it.
- **No `deactivated_at` date on a row** — see `Assumed:`, item M.

**Assumed:**
- **A.** The username preview mirrors `domain-modeling.md §5.1` (normalize → base → collision suffix on the final assembled string) in client code, using the account list already on screen as the "taken" set, because S1.8 requires the auto username be "shown read-only" at create time and no preview endpoint exists. Duplicated algorithm, deliberately: the copy is a preview only, the server assigns the real value, and the screen reports the server's answer after the create rather than the preview.
- **B.** `ADMIN` is **not offered** in the create form's tier row (Volunteer/Staff only), while the edit form offers all three. S1.8's Accounts bullet literally says "assign tier (Volunteer/Staff/Admin)"; cap 1 says Admin "creates/deletes **non-admin** accounts", and `services/user.ts` answers 403 to a create at ADMIN. I read the create/edit split as cap 1's, not as a contradiction of S1.8.
- **C.** No Devices sub-screen, on the reading above (S1.8 Layout's "four sub-screens" + S1.5's "the receiver tablet's device registration is itself Phase 2"). If Phase 1 is meant to be able to register the shared desktop, this is the gap.
- **D.** No Routes sub-screen; `/routes` is treated as S1.6's.
- **E.** **A deactivated account cannot be reactivated from this screen, because nothing can do it.** `UpdateUserRequest` has no `active` field and there is no user restore route — `POST /routes/:id/restore` is the pickup-route one. Donors, trucks and categories *can* be restored with `PATCH { active: true }`. I did not invent a path; the asymmetry is reported. A deactivated account renders with a chip and a sentence, and its details stay editable (I21: "field edits are always allowed").
- **F.** The "In use ⇄ Archived/Inactive/Deactivated" toggle is offered on **all three** master edit forms, not only Categories. S1.8 names "archive" only for categories and says "add/edit/delete" for donors and trucks; `UpdateDonorRequest`/`UpdateTruckRequest` both carry `active` as §3.3's lifecycle toggle, and I21 makes it a field edit. Reading: the toggle is an edit, so "edit" covers it.
- **G.** An edit that changes **only** the credential goes to `POST /users/:id/credential`; any edit that changes something else carries the credential inside the single `PATCH`, so a tier change and its required new password cannot half-apply. No doc says which of the two paths S1.8's "set/reset PIN or password" is.
- **H.** `CreatedAccount` (`{ user, generatedCredential? }`) is declared in this lane's `api.ts`, because `shared/src` has no type for `POST /users`' 201 body — `routes/users.ts` assembles it inline. Not added to `shared/`, which is single-owner.
- **I.** Five small pieces built inside this folder because `components/index.ts` exports nothing for them: `FieldGroup` (a labelled group around a non-input control), `ReadOnlyValue` (the username), `InactiveChip` (which **reuses** §3's existing `r3-chip r3-chip--muted` classes rather than redefining the look — `StatusChip` takes `ShiftStatus` only and does not fit a master record), `DutyToggles`, and `CredentialField`. Promote any of them only if a second lane wants it.
- **J.** While an admin sets someone's PIN, the digits are shown **in the clear** (unlike S1.1's dots) because the admin has to read the number back to that person; a password stays masked, with copy saying to pass it on. §3 gives the keypad, not this choice.
- **K.** The word for out-of-use per entity — Deactivated (account, donor) / Inactive (truck) / Archived (category) — is taken from `shared/src/masters.ts`'s note that the label differs per entity in the UI and nowhere else. `ui-ux-spec.md` does not spell the three words out.
- **L.** Which tab is open is **local state, not in the URL**: `/admin` has no sub-path and `app/routes.ts` is lead-owned, so a sub-screen is not deep-linkable and a reload returns to Accounts.
- **M.** Master rows show **no "deactivated since" date**, because `DonorSummary`/`TruckSummary`/`CategorySummary` carry only `active`. Worth a look at merge: `services/donor.ts` explains its no-restamp branch with *"'deactivated since' is information the admin screen shows"* — the wire has no such field, so either that comment is stale or `shared/` owes one. Both files are single-owner, so I changed neither.
- **N.** No timestamp is rendered anywhere on this screen, so A120's pantry-timezone rule never comes up. `createdAt` arrives on all three master shapes and is deliberately not shown.
- **O.** **`doc-qa` was not run by this lane.** The agent-spawning tool is not available in this context, so I could not run it despite `CLAUDE.md`'s pre-commit instruction. Gate part 2 (§5.2) is the lead's over the merged diff; this is a note, not a request.
