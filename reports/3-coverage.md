- *Two drivers, one run.* Both snapshots see `OPEN`, both pass the gate, and the loser's UPDATE meets a row a committed transaction has changed — `40001`, "could not serialize access due to concurrent update". A third test runs the same race through the public `claimShift`, where `writeTransaction` retries the 40001 and the retry re-reads a board on which the run is gone, producing "That run was just taken by Karen."
- *One driver, two overlapping runs — `architecture.md §4.1`'s canonical write-skew case.* Both gates read "no overlapping owned shift" and both are right when they read it; the two rows written are different, so no row lock and no tier-2 predicate sees anything wrong. The test asserts the loser fails with `40001` "could not serialize access due to **read/write dependencies** among transactions", and that exactly one run ends up owned. That assertion is the justification for §4.1's isolation decision, executing.

**Assumed:**
- **`uq_notif_shift_event` swallows a second `SHIFT_OPENED` for the same (run, recipient).** The index is `(event, shift_id, recipient_id)` with no filter on which events it covers, while `0006`'s comment justifies it as needed "only [for] shift-scoped, time-triggered events; event-triggered ones fire once by construction". `SHIFT_OPENED` is event-triggered and does **not** fire once by construction — a run can be released, re-claimed and released again. The second fan-out is therefore absorbed and nobody is told. I did not work around it (the fix is a migration, which is lead-owned) and instead **pinned the behaviour with a test** so it is visible. This is the one entry here I would escalate first.
- **The I20 staff-assign exemption is scoped to the two temporal reasons.** `AVAILABILITY_BLOCK` and `OWNED_SHIFT_OVERLAP` are confirmable; `NO_DRIVE_DUTY`, `DEACTIVATED` and `UNKNOWN_USER` are hard refusals for Staff as much as for self-select. The I20 note names exactly "the driver's declared availability or another owned shift", and a user with no Drive duty is not a driver to override a conflict about. No doc says what Staff may *not* confirm through.
- **Staff-assign and staff-unassign are restricted to `OPEN` and `CLAIMED`.** An `IN_PROGRESS` run's driver cannot be changed wholesale. Inferred from I30 existing at all — mid-run reassignment moves *stops*, close-old + insert-new, precisely because the shift is not the unit that moves (its truck is picked, I8, and its stops are snapshotted, I5). No doc states this bound.
- **Reassigning a `CLAIMED` run to a different driver notifies only the new owner.** The matrix has no "you were removed from a run" event and I read it as closed, so the previous owner is told nothing. (Staff-*unassign* does notify them, because that run returns to the board and the matrix covers that.)
- **A self-select claim notifies nobody.** The matrix's "Shift assigned / defaulted to you" is read as the staff-assign path; telling a driver what they just did themselves is not in it.
- **The actor is excluded from the `SHIFT_OPENED` fan-out.** A driver releasing a run is, one statement later, an eligible driver for it; the coordinator who unassigns is a coordinator. The matrix says "Coordinator + eligible drivers" without saying whether the person who caused the event is one of them. Consequence worth knowing: at this org's headcount (PRD §6, one coordinator) a staff unassign sends no coordinator row at all.
- **Claiming has no time bound.** `data-model.md §9`'s claim predicate is `status='OPEN' AND owner_id IS NULL` and nothing else, and no doc forbids claiming a run whose window has passed, so I added no clause. Release *is* bounded (`starts_at > now()`) because cap 8 says "before it starts" in as many words. The asymmetry is deliberate.
- **§5.3's "existing future OPEN instances" is `starts_at > now()`, plus the run the driver actually tapped, always.** That keeps SERIES a superset of ONE even for a run starting within the hour. No doc fixes the boundary.
- **`claim-all` sets `ownerDefault` unconditionally**, including when every existing run was skipped. §5.3 states the two clauses independently, and each future run is gated again at materialization by I25.
- **A series claim reports skips rather than failing**, even when the driver is ineligible for every run in it (result: `claimed: []`, `partial: true`). The one thing that fails outright is the tapped run no longer being OPEN, because a partial-success report for a claim that never had a chance would be misleading.
- **`release-range` defaults `fromDate` to the tapped run's own date and treats a missing `toDate` as open-ended**, which is S1.3's "this and future". It touches only runs of the same pattern owned by the actor. §5.3 says "instances in [from, to]" without saying of what, or what an absent bound means.
- **A range release silently omits a run that moved on since the read; a single release explains the refusal.** No doc covers the partial case for release the way S1.2 covers it for claim.
- **The at-risk sweep alerts once per run, not once per recipient-becoming-eligible.** Due is `OPEN ∧ now() < starts_at ≤ now() + interval '1 day'`; unhandled is "no `SHIFT_AT_RISK` row exists for this run". A driver who becomes eligible *after* the first alert is not alerted later. §4.4 says "1 day before an unclaimed shift" and does not say whether the set is re-evaluated.
- **Every user-visible sentence in this lane is mine except three**: S1.2's partial-success summary, §6's "That run was just taken by Karen.", and S1.6's assign warning. That includes generalizing S1.6's "Karen marked herself away then" to a neutral pronoun ("marked themselves away"), the multi-weekday series label ("Tuesday and Friday"; "repeating" at three or more, since a toast should not recite a list), and the double-tap answers "That run is already yours." / "That run is already back on the board." — the alternative for the latter was a 403, which is both harsh and untrue for someone who released it a second earlier.

- **The transactional core `claimShiftIn(tx, …)` is exported alongside `claimShift`.** The public entry is still one function per domain operation; the core exists so a test can put a barrier between the gate's read and its write, which is the only way to make the write-skew interleaving deterministic rather than lucky. `services/notification.ts` sets the precedent for a `tx`-taking export.
