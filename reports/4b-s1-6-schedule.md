**Built:**
- `S1.6 Staff — shift & route scheduling` at `/schedule`, three panels behind the §3 segmented control in its `tabs` behavior (Runs · Repeating runs · Routes), one on screen at a time.
- Publish one run: route + day + start/end time + optional driver note. **No truck field and no driver field** (I8; PRD cap 4 — runs exist with no driver). Pantry-local `YYYY-MM-DD`/`HH:MM` text only, never an instant.
- The recurring builder: route, weekday toggles, times, and `endDate` or "no end". **"Starting __" is a computed read-only sentence**, not an input (A111) — "Every Tuesday, starting Aug 4, no end."
- "Edit just this date" vs "Edit the weekly pattern" as a two-button prompt on any run minted from a pattern (PRD cap 4); the pattern branch hands off to the Repeating tab with that rule loaded.
- Per-run editor: coordinator→driver note (cap 11 ch.1), set/clear driver, "Move the date or time" → S1.7, cancel the run.
- Assign-as-warning: tap a name → `GET /shifts/:id/eligibility` → inline warning → **"Assign anyway"** re-posts with `confirmConflict`. **The assignment is never blocked by a conflict staff has seen** (I20's staff-assign exemption).
- Pattern-level edit (I24) reporting all three outcomes the server distinguishes (runs moved, runs left because they have a driver, runs left because they are off-pattern), plus staff's bulk-terminate over a date range with a confirm naming that it is terminal and *not* a release.
- Route builder: ordered stores, **drag-and-drop plus Move up / Move down**, add from the store list, delete/archive with the I21 outcome reported, restore an archived route.
- Times render in `useSession().timezone` throughout (A120); pantry-today and pantry-now are derived from it. Zero device-clock reads in the folder (`getFullYear`/`getMonth`/`getHours`/`toLocale*`: none).

**Assumed:**
- **The route builder ships BOTH drag-and-drop and Move up / Move down, and A117 was read as specific to S1.5.** `ui-ux-spec.md S1.6` says "drag-and-drop ordering with large handles" and `product-requirement.md` cap 4 — the higher-authority doc — says "defines/edits routes as ordered stores (drag-and-drop ordering)", so drag is specified for *this* screen by both. A117 removed drag from S1.5, whose reorder is a driver's `ShiftStop` list on a phone in a moving truck; it did not amend cap 4 or S1.6. Drag is implemented with native HTML5 drag events, so no dependency is added and nothing is a hand-rolled pointer drag (§1.5). Move up / Move down is not a fallback but the required equivalent: HTML5 drag events do not fire on touch at all and the responsive matrix marks Scheduling "usable" on a tablet, and a keyboard user has no drag gesture — §1's 44px/accessibility floor does not lift because the canonical device has a mouse. Both go through the same two pure functions so they cannot disagree about what an order is.
- **The screen's layout is three tabs — Runs · Repeating runs · Routes.** S1.6 lists four capabilities and names no layout. §4 gives staff one desktop nav entry ("Schedule (publish, routes, reschedule, assign)"), §1.5 rules out a dropdown, and S1.8's four-tab admin shell is the in-repo precedent, so the §3 segmented control in `tabs` mode (with `idPrefix` + `tabPanelProps`) carries it. Reschedule is the fourth item in §4's list and is S1.7, reached by a link.
- **Each panel is in exactly one of three modes so that exactly one primary button is on screen (§1.1).** This is why "Publish a run" *opens* a form rather than the form sitting permanently above a list that has its own Save, and why the top-level primary hides while a run is being edited. S1.6 says only "Primary action: Publish / Save".
- **Four input controls were built inside this lane's own folder** because `components/index.ts` exports none of them: `DayPicker` (a visible month of day targets, single or two-tap range), `TimeChoice` (a grid of half-hour buttons, 5am–10pm), `WeekdayChoice` (seven toggles) and `ChoiceList` (a visible list to pick one of). All follow S1.4's precedent for the same problem. **Candidates for promotion to `components/` if another lane wants one** — S1.4 has its own `DayRangePicker` and its own `timeOptions`, so the day/time controls are now duplicated in two lanes and are the strongest candidates.
- **What "Edit just this date" actually edits is the lane's composition.** `PATCH /shifts/:id` accepts only `staffNote`, so the per-run editor is: the note, set/clear driver, "Move the date or time" (→ S1.7) and "Cancel this run". S1.6 names the *label* but not the field list. Note this overlaps S1.3, which also lets staff edit `staff_note` on desktop.
- **The computed "starting" date mirrors materialization's "window has already begun" filter**, so a Tuesday rule saved on a Tuesday afternoon displays *next* Tuesday. No doc says the display should account for that; naming today would name a run `services/recurrence.ts` will not mint, and the point of a read-only sentence is that it is true.
- **Pantry-today and pantry-now are derived client-side from `useSession().timezone` via `Intl.DateTimeFormat`.** A120 exposes the zone but no endpoint exposes the pantry's current date, and the day picker's "today" and the computed start date both need it. The device zone remains the fallback for the one render before the session loads.
- **Route delete / archive / restore is on this screen**, though S1.6's bullets list only define/edit/order/add-store. The endpoints exist (`DELETE /routes/:id`, `POST /routes/:id/restore`), no other Phase-1 screen owns routes (S1.8's four tabs are Accounts/Donors/Trucks/Categories), and without it a mistyped route stays in the publish picker forever. Removal reports which of delete/archive I21 chose rather than asking staff to choose. An archived route must be restored before it can be edited.
- **Staff-assign sets only `shift.owner_id`, never the pattern's `ownerDefault`.** Cap 6's "Staff assigns/defaults a driver" could be read as also setting the series default, and `shared/src/schedule.ts` comments `ownerDefaultId` as "Set by claim-all / **staff-assign**". But `POST /shifts/:id/assign` takes no scope, `services/coverage.ts` sets `owner_default_id` only on the driver's claim-all path, and S1.6's own gloss is "Same owner field as self-select" — which is `shift.owner_id`. I built the per-run assign and did **not** report this as blocked, because the screen's own sentence points at the single-run field. **If cap 6 was meant to give staff a series-level default, the endpoint for it does not exist and this is a Wave-3 gap.**
- **The runs list is bounded to today forward** (`?from=<pantry today>`, no `to`, cancelled runs excluded) — the same choice as A121 for the board, for the same reason: the far end is already bounded by `app_config.horizon_days`.
- **Day grouping, the "Today/Tomorrow" headings, and the calendar/wall-clock helpers are duplicated** in this folder rather than shared, because the existing copies live in `s1-2-board/board.ts` and `s1-4-my-shifts/logic.ts` — other lanes' folders. Three copies of `formatTimeLabel`/`timeOptions` now exist. A consolidation candidate whenever a shared client-utils owner is named (cf. A128 for wire types).
- **The pattern-edit report sentences are the lane's** — how to word "1 run already has a driver and was left where it is", "N runs are no longer on this pattern and stay on the board". `UpdatePatternResponse` returns the three counts and no doc gives copy for them, but staff has to be told, because §5.3 retracts nothing already materialized and cap 9 is why an owned run was not moved.
- **All user-visible copy on this screen is the lane's, unread by a human** — roughly 90 sentences, same standing as A6/A45/A70/A92/A107/A129. Pinned by tests against §7's forbidden words, against any sentence asking staff for a truck, and for the presence of "a run can go up with no driver".
