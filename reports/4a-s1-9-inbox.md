**Invariants:**
- **I1**, tier-3 — hierarchical, via the `{ tier: 'VOLUNTEER' }` declaration on all four routes and `accessGate`'s `tierAtLeast`. "Any signed-in user"; no duty gate, because the inbox is not a driver surface (a coordinator receives `UNAVAILABILITY_DECLARED` and `SHIFT_AT_RISK`).
- **No I1–I30 invariant is owned by this lane.** What is enforced here is `architecture.md §4.1` (both writes in `writeTransaction`, `SERIALIZABLE` + retry; nothing outside `services/` opens one), `§4.3` (default-deny; the "whose inbox" rule is in the service because it needs the row, not the session), and `data-model.md §11`'s device-scoped carve-out.
- **Device-scoped exclusion**, tier-3, by construction: `recipient_id = actor.id` cannot match `recipient_id IS NULL`. `ck_notif_recipient` (tier 1) is what makes those rows the only ones with a null recipient. Asserted in two tests, one of which checks the row is still unread afterwards.
- **Ownership is in the write predicate**, not a check taken beforehand: `markRead`'s UPDATE carries `recipient_id = actor.id AND read_at IS NULL`, so idempotency and ownership hold under concurrency rather than under discipline.
- `pii.ts` has no role: no `app_user` row is read on any path here. A notification carries at most a rendered first name (`payload.who`), and names are never gated (`pii.ts`, `product-requirement.md §2`).

**`./scripts/gate.sh` is RED, and not because of this lane.** Full server suite: 525 passing / 2 failing, both in `server/test/recurrence-materialization.test.ts` (Wave 3's file, already on `phase-1`, outside this lane's ownership and untouched by it):

- `a pattern-level edit is the one thing that does change it (I24)`
- `moves the future UNCLAIMED instances onto a new window, and reports the count honestly`

**Diagnosis (verified, not guessed).** Both are wall-clock dependent. The fixture materializes an EVERY_DAY pattern at `start_time` `09:00`, then `updatePattern` moves it to `13:00` — and `updatePattern` re-materializes at the end (`services/recurrence.ts`, `materializeIn(tx, patternId, new Date())`). When pantry-local *now* falls between 09:00 and 13:00, today's 09:00 occurrence was skipped as past at the first materialization and today's 13:00 occurrence is generated by the second, so `after` holds an instance `before` does not and `before.find(...)!` is `undefined`. Proof: the same commit passed the full gate at 07:47 local and fails at 12:57; setting the test database's `app_config.timezone` to `Pacific/Honolulu` (pantry-local ≈ 02:58) makes all 26 tests in that file pass, and restoring it fails them again. Nothing else changed.

The fix belongs to whoever owns that file — most cheaply, seed the pattern at a time-of-day that cannot straddle "now" (e.g. materialize with an explicit `startTime` well before the edited one and assert against the intersection), or compare only instances present in both sets. **This lane did not touch it**: it asserts I24, and relaxing an invariant's test to get a green gate is exactly what the build plan forbids.

**Assumed:**

*Every endpoint path, response shape and mark-read semantic below is this lane's design. No foundation doc specifies any of it.*

1. **Paths.** `GET /api/notifications`, `GET /api/notifications/unread-count`, `POST /api/notifications/read-all`, `POST /api/notifications/:id/read`. Chosen to follow the established `POST /shifts/:id/<action>` shape (`routes/coverage.ts`, `routes/execution.ts`). `/notifications` is claimed by no earlier module, so no method+path pair is shadowed (A108).
2. **Access.** All four declare `{ tier: 'VOLUNTEER' }` with **no duty**. A user with an empty inbox reads an empty inbox rather than a 403.
3. **No subject parameter.** There is no `?userId=` and no staff or admin view of another person's inbox — unlike `GET /availability`, which has one. Rows are per-recipient and the PRD gives no reader other than the recipient.
4. **Response shapes.** `GET /notifications` → `{ items: InboxItem[], unreadCount: number }`; `GET /notifications/unread-count` → `{ unreadCount }`; `POST /:id/read` → `{ id, readAt, unreadCount }`; `POST /read-all` → `{ marked, unreadCount }`.
5. **`InboxItem`** = `{ id, event, title, detail: string | null, url, shiftId, read: boolean, createdAt, when }`. `read` is a boolean rather than the raw `read_at`, since the screen only ever asks "dot or no dot".
6. **`unreadCount` rides along with the list and with every write**, so the list and the bell can never disagree by one refresh.
7. **Query parameters** `?unread=true` and `?limit=`. Default page 50, hard cap 200 (`INBOX_PAGE_DEFAULT` / `INBOX_PAGE_MAX`). `?unread=true` narrows the rows but never the count.
8. **"Newest first" is `created_at DESC, id DESC`.** The tie-break is not decorative: one fan-out writes several rows in a single transaction, so they share `now()` exactly and an untied list visibly reshuffles between refreshes.
9. **Mark-read is idempotent and the first `read_at` wins.** A second tap is not a second reading.
10. **Another user's row, an unknown id and a malformed uuid all answer 404** with the same message — never 403 — so the inbox cannot be probed for whether an id belongs to someone else. A malformed uuid is short-circuited before it reaches Postgres, which would answer `22P02` and surface as a 500.
11. **Mark-all-read exists.** S1.9 does not mention it. Built because tapping a row *navigates away*, so a coordinator fanned out to a dozen open runs would otherwise clear the bell one round trip at a time. Rendered as a secondary button, so §1 principle 1 still holds.
12. **Row copy is `renderPush()`'s, not a second set of strings.** `title` is reused verbatim; `detail` is `[payload.when, payload.route]` joined with " — ", which is the same string `renderPush` builds. The banner's fallback body ("Open R3 to see the details.") is dropped — the reader of an inbox row is already in R3.
13. **`url` is `renderPush()`'s verbatim**, so the row's tap target, the banner's tap target and what `sw.ts` posts to the running app are one destination (`/shifts/:id`, else `/inbox`). A shiftless row's tap therefore navigates to the path it is already on, which `router.tsx` treats as a no-op.
14. **Arrival time is formatted on the server** in `app_config.timezone`, following the `payload.when` precedent (A7): the browser does not know the pantry's zone, and a driver whose phone is elsewhere must still read the pantry's clock. Under 7 days old → `"Tue 9:00 AM"`; older → `"Aug 4"`. The 7-day cut and both formats are this lane's.
15. **`createdAt` (ISO) is returned alongside the formatted `when`**, unused by the screen today, so a later consumer does not have to parse a display string.
16. **`event` is returned but never rendered** (`ui-ux-spec.md §7` — it is vocabulary, not copy).
17. **The wire types are declared twice**, in `server/src/routes/notifications.ts` and in `client/src/screens/s1-rescue/s1-9-inbox/api.ts`. `shared/src/` is single-owner and forbidden to a wave-4 lane; the duplication is the deliberate trade, per the brief.
18. **Read state is never un-set.** No "mark unread" endpoint, and no path clears `read_at`.
19. **Screen copy** (all in `inbox.ts`'s `COPY`, held against §7's forbidden list by a test): title "Inbox"; action "Mark all as read"; empty "Nothing here yet." / "You'll see the runs you're on, a reminder an hour before each one, and runs that still need a driver."; failures "Couldn't mark that as read. Try again." and "Couldn't update your inbox. Try again."; 404 message "That alert is no longer in your inbox." Nothing implies a run finishes (D1), and a test asserts that.
20. **A row reads as `${title} — ${detail}`**, or just `title` when there is no run behind the event. `InboxRow` takes one `text`, so the two halves are joined rather than stacked.
21. **Tapping an unread row marks it read optimistically, then navigates.** The dot and the count move before the server answers, because the tap usually unmounts the list. A failed mark shows an error toast; the row is not reverted, since by then the screen is normally gone.
22. **The screen does not poll.** It loads once and reloads only through §6's user-initiated retry. Only the bell (`useUnreadCount`) refreshes on its own.
23. **`useUnreadCount` polls every 60s and on `visibilitychange`.** No doc gives an interval. A notification is written by a job or another user's action, so nothing in this browser learns of it otherwise, and push cannot be relied on to (PRD channel strategy). A failed poll is swallowed — it is ambient information the user cannot act on.
24. **The header renders the push-state chip from its own `usePwa(true)` instance**, a second one alongside the shell's. §5 puts the chip in the inbox header and `usePwa` is the only exported way to get its "tap to fix"; its start-up work (worker registration, re-offering an existing registration) is documented idempotent, which is what makes a second instance safe. The alternative was passing the shell's value down through `AppShell`, which is not this lane's file.
25. **Layout:** one column capped at 44rem, header wrapping to a second line on a narrow phone. S1.9 is canonical on phone *and* desktop, so desktop widens the padding, not the line length.
26. **`server/src/routes/index.ts` registers `notificationRoutes` last**, after Wave 3's three shift modules.
