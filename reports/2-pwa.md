**Status:** complete

**Built:**
- **Installability**: a web app manifest (`/manifest.webmanifest`) with `standalone` display, brand-token icons in `any` and `maskable` purposes, and the `<link rel="manifest">` added at startup from `main.tsx`.
- **Service-worker registration** at `/sw.js` — the fixed unhashed path A14 promised, exercised for the first time by this lane and verified against a real `vite build`. Registration only; `sw.ts` itself is untouched and still has no `fetch` listener (`architecture.md §4.5`).
- **The §5 onboarding flow as a pure state machine** (`pwa/onboarding.ts`): platform-aware install guide (iOS vs Android, two steps each), then the single "Turn on alerts" prompt, then a "blocked" card that says what to do about a refused permission. Every card is dismissible and none blocks the app.
- **iOS is told plainly that installing comes first** — on iOS the guide is the whole flow, because `Notification` does not exist in a tab and offering "turn on alerts" there would be offering a button that cannot work.
- **The permission + registration path** (`pwa/alerts.ts`): permission → worker → the box's VAPID public key → `pushManager.subscribe` → `POST /api/push/subscriptions`, plus a silent `syncRegistration()` on every start that re-offers what the browser already holds. That idempotent re-offer is the entire recovery story for a registration the server never received.
- **The §5 push-state chip is live**: `App.tsx` feeds `AppShell`'s `alertsEnabled` / `onFixAlerts` from the hook, and "tap to fix" re-walks the permission flow in the same user gesture.
- **Tapping an alert now lands somewhere**: `sw.ts` posts `{ type: 'navigate', url }` to a focused window and nothing was listening; `App.tsx` now routes it (S1.9 "tap to act").
- **Server**: `POST /api/push/subscriptions` (idempotent upsert on `uq_push_endpoint`, un-revokes a re-offered endpoint) and `GET /api/push/config`, both declaring `{ tier: 'VOLUNTEER' }`. Which owner a registration gets — person or shared device — is decided server-side from the confirmed `r3_device` marker, never from anything the client sends.
- **A15 closed**: verified `client/src/api/session.ts` already re-exports the published `ShapedUser`/`SessionResponse` rather than a local copy (the lead did this at the Wave-1 merge). This lane repointed the import (see below) and nothing else was owed.
- **A34 extended to the browser half**: `client/src/api/shared.ts` re-exports `shared/src/index.ts` by relative path, and the five client files that said `@r3/shared` now go through it. In a worktree, `node_modules/@r3/shared` resolves to the **main checkout's** `shared/src`, so this lane's own additions to `shared/src/index.ts` were invisible to its own client typecheck — verified with `tsc --traceResolution`, not assumed.

**Deliberately not done:**
- **Nothing rendered is tested.** There is no browser or component harness in this repo and adding one (jsdom, a renderer) would be a dependency, which a lane may not add (build-plan §3/D5). The flow was written as pure functions of a plain record *so that* it could be tested at all; `Onboarding.tsx`, `usePwa.ts` and the browser calls in `alerts.ts` are covered by typecheck and by the shape of the code, not by a test.
- **No unregister / "turn alerts off" endpoint.** §5 offers only "Alerts OFF — tap to fix", and a dead registration is soft-revoked by dispatch on a `410` (A4). Adding a delete path would contradict `data-model.md §0`.
- **The inbox header's chip.** §5 puts the chip in the inbox header as well as the top bar; S1.9 is Wave 4. The top-bar chip is live now, and `usePwa()` is exported for the inbox screen to use the same state rather than deriving a second one.
- **No illustrations.** §5 asks for a "2-step illustration"; each guide renders two large numbered steps instead — see `Assumed:`.
- **Truck-inbound.** Phase 2 (PRD §4). Device-scoped registrations are stored correctly now, and no Phase-1 event targets one, which the dispatch test asserts rather than assumes.
- **`doc-qa` was not run by this lane** — this agent has no tool to spawn another agent (the same gap Wave 1's lanes reported). Per build-plan §5.2 the lead runs it over the merged diff; that step is still owed on this work.

**Assumed:**
1. *The manifest `<link>` is injected at runtime from `main.tsx`, not declared in `client/index.html`.* `client/index.html` is outside this lane's declared file ownership, so it was left alone; Chromium honours a manifest link added to the head, but a static `<link rel="manifest" href="/manifest.webmanifest">` in the document is the correct end state and is a one-line change for the lead. The same file is also where `<link rel="apple-touch-icon">` belongs — iOS uses it for the home-screen icon and ignores the manifest for that, so on iOS the installed icon is currently the browser's own screenshot fallback.
2. *`client/public/` was created by this lane although ownership says `client/src/**`.* A manifest and its icons cannot be served from `src` at a stable URL. New files, no existing owner, no concurrent lane under `client/`. Revert is `rm -r client/public` plus dropping `linkManifest()`.
3. *Onboarding runs only once someone is signed in.* §5 says "First visit on phone shows a one-card guide" and does not say whether that is before or after login. Registering requires a session (the routes declare a tier), and §5 lists onboarding under "Auth & onboarding" after login, so the login screen stays a login screen.
4. *§5's "matching 2-step illustration" is rendered as two large numbered text steps, not artwork.* No illustration assets exist in the repo and producing them is not a lane's job. The platform-specific *wording* is there ("Tap the Share button at the bottom of Safari" vs "Tap the menu button at the top right of your browser").
5. *All onboarding copy is this lane's.* No doc fixes the strings beyond §5's two quoted sentences, which are used almost verbatim. Everything else — the step wording, "Alerts are blocked", and the reassurance line on every card — was written to §7 and is asserted against §7's forbidden-word list, but **no human has read it**. Same class of assumption as A6.
6. *Dismissal is remembered in `localStorage` per browser, under `r3.alerts.dismissed`.* Nothing says where "first visit" state lives; no table holds it and migrations are lead-owned. Losing it costs one dismissible card, and the chip clears it on "tap to fix".
7. *A browser presenting a valid `r3_device` marker registers **device-scoped**, never user-scoped.* The docs state the tablet holds a device-level registration (`PRD §2`, `architecture.md §4.2`) but never say what happens when a driver enables alerts while signed in at that tablet. Reading chosen: the device owns it, so a driver's personal run alerts never fire on a shared machine in the pantry — and it keeps §4.2's "losing the marker also stops the alerts" property intact. The alternative (user-scoped on a shared device) would leak one person's alerts onto a device a dozen people use.
8. *Re-offering an endpoint clears `revoked_at`.* A4 settled that a `410` revokes rather than deletes, and `uq_push_endpoint` makes a second live row for the same endpoint impossible — so clearing the timestamp is the only route back to live. No doc addresses the resurrection case.
9. *An endpoint must be an absolute `https` URL and each key base64url; nothing else is validated.* No doc constrains the registration payload. Deliberately loose: the gateway and `web-push` are the authorities on their own encoding.
10. *`push_subscription.label` carries a device description from the client* ("Android phone (home screen)"). `data-model.md §11` declares the column and says nothing about its contents. It never reaches a screen.
11. *`GET /api/push/config` returns `{ publicKey: null }` on a box with no VAPID rather than failing.* The same degradation A12 chose for dispatch, for the same reason: the inbox is the source of truth, so an unconfigured box loses the alerting layer and nothing else. The client then shows no alerts card at all, because nagging about a state no volunteer can change would break §5's "the app is fully usable with alerts off".
12. *The five existing client files that imported `@r3/shared` were repointed to `client/src/api/shared.ts`.* Inside this lane's ownership but authored by Wave 1's `surface` lane. Not cosmetic: `@r3/shared` resolves to the **main checkout's** `shared/src` from inside a worktree, so a lane editing that file typechecks its client against a different file than the one it is writing. This is A34's hazard on the browser side; A34 is still open for the server, which already imports by relative path.
13. *The phone breakpoint is repeated as a literal `767px` in `pwa.css`.* The onboarding card is a sibling of the shell rather than a descendant, so it cannot use the `r3-app--phone` class, and a CSS custom property cannot appear in a media query. The value tracks A16 and `tokens/index.ts`.
