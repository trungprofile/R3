# QA Round 2 — Pass 2: Receiver persona, shared tablet (1024×768)

Role simulated: `luispark` — VOLUNTEER, `DRIVE` + `RECEIVE`. Viewport target: shared tablet landscape 1024×768 per the pass brief.

**Viewport note on method:** `resize_window` did not reliably produce a true 1024×768 outer browser viewport in this environment (it read back as clamped/inconsistent at points during the session). Per the fallback in the harness instructions, a same-origin iframe was used to get a faithful 1024×768 (and later 1023×768) layout viewport for DOM measurement and screenshotting. This iframe technique is what surfaced Defect 1 below — the iframe's `window.innerWidth` reported exactly `1024` for a `1024px`-wide box, which is what exposed the boundary bug. Screenshots in this pass are of the iframe content; DOM overflow/tap-target checks were done via `getBoundingClientRect()` against the iframe's own `document`, which is authoritative regardless of the outer tab's rendered/clipped size.

## Defects

### Defect 1 — Canonical shared-tablet width (1024px) is misclassified as desktop; receiver has no way to the receive screens
Screen: S1.1 Login → home redirect (`app/routes.ts` `homePathFor`), affects S2.1b/S2.2/S2.2b/S2.3 reachability
Severity: **blocker**
Device/viewport tested: shared tablet, 1024×768 (the pass's own canonical size)
Role simulated: Volunteer, DRIVE + RECEIVE (`luispark`)
Expected (spec citation): `ui-ux-spec.md §4`, "Tablet (receive): no nav. Login → Weight entry." and S2.1: "Opens to S2.1b (run picker)." Also `phases-1-3.md` A167: "a receiver at the shared tablet lands on the run picker... Landing them on the board at the tablet would be a dead end — that surface has no navigation at all."
Actual: `client/src/app/useViewport.ts` classifies viewport with `if (width >= breakpoint.desktopMinPx) return 'desktop'` where `breakpoint.desktopMinPx = 1024` (`client/src/tokens/index.ts`). A box that is exactly `1024px` wide (confirmed via `window.innerWidth === 1024` inside the iframe, no scrollbar deduction) is therefore classified `'desktop'`, not `'tablet'`. Because `homePathFor()` (`client/src/app/routes.ts:152-159`) only redirects a signing-in RECEIVE-duty user to `/receive` when `viewport === 'tablet'`, a device rendering at exactly 1024 CSS px — the pass's own stated canonical tablet size, and a genuinely common tablet landscape resolution (e.g. the classic iPad) — instead lands the receiver on `/board` with the **full desktop left nav** (`Board · My Shifts · Inbox` for this duty combination). That nav has **no entry to Receive at all** at any viewport (`nav.tsx` `navItemsFor` never lists a receive/weight-entry item for the desktop or tablet case — tablet returns `[]` by design, and desktop's list is Admin/Schedule/Report/Board/My Shifts/Inbox only). A receiver on a real kiosk-style tablet at exactly this width has no on-screen control that reaches S2.1b/S2.2/S2.3 — only typing `/receive` into an address bar gets there, which a locked-down shared device may not offer. Confirmed by dropping the iframe to 1023px: the same login flow correctly redirects to `/receive` with no nav, matching spec.
Repro steps:
  1. Set the browser viewport to exactly 1024×768 (this pass's stated canonical tablet size).
  2. Sign in as a Volunteer holding the RECEIVE duty (`luispark` / `4321`).
  3. Observe landing on `/board` with a full desktop-style nav sidebar, not `/receive`.
  4. Note the nav offers Board / My Shifts / Inbox and nothing that leads to weight entry.
  5. Repeat at 1023×768: login correctly redirects to `/receive`, no nav shown.
Screenshot: not saved (see repro; DOM-verified via `window.innerWidth` and `homePathFor` source reading, cross-checked against live behavior at 1024 vs 1023).
Fix suggestion: either make the tablet band inclusive of 1024 (`desktopMinPx: 1025` or `width > breakpoint.desktopMinPx`), or pick breakpoints that don't collide with the stated canonical resolution.

### Defect 2 — "Finish this run?" confirm promises a fix path the receiver themself no longer has, once past the edit window
Screen: S2.2b Receive done (confirm modal)
Severity: minor
Device/viewport tested: tablet, 1023×768 (see viewport note above)
Role simulated: Volunteer, DRIVE + RECEIVE (`luispark`)
Expected (spec citation): `ui-ux-spec.md §7` microcopy rules: copy should tell the reader "why something is blocked" and not mislead. The D9 test in this pass's brief expects the receiver to be refused edits outside the window "with words that point at the Reporter."
Actual: The `receiveDone` confirm modal always reads "This closes out the run. You can still fix a weight afterwards," regardless of whether the receiver's own edit window (`receiver_edit_window_days`) has already closed for that run. For the D9 fixture (a run picked up 15 days ago), this is confirmed false from the *receiver's own* vantage point at this tablet — attempting the edit is refused with "The time to change this run has passed. Ask someone with reporting access to fix it." (correct, and it does point at the Reporter). But the reassurance in the *Finish this run?* modal, read by the same receiver seconds earlier/later, implies "you" (the person tapping the button) can still fix it, which for this state is not true — only a Reporter can. Not severe (the modal is still accurate in the common case, and the correct refusal does appear when actually attempting an edit), but it is one sentence of reassurance that this pass's own D9 fixture directly contradicts.
Repro steps:
  1. Open the D9 fixture run (a fully-weighed, never-closed run older than `receiver_edit_window_days`) at S2.2b.
  2. Tap "Receive done."
  3. Read the modal's second sentence.
  4. Compare against attempting an edit on that same run's stop: refused, pointing at the Reporter.
Screenshot: `ss_5642glj1c` (modal, generic run within window), `ss_6934dkr26` (the correct D9 refusal toast for comparison).

## Open questions / Untestable from here

- **S2.4 truck-inbound banner (A171: must not steal the keypad):** could not get the banner to render in this harness. The delivery path is a real service-worker `postMessage`, which requires an actual push subscription (`architecture.md §4.5`) — out of reach for browser automation per this harness's stated limitations. I attempted to simulate it by dispatching a synthetic `MessageEvent` directly on `navigator.serviceWorker` (the exact `ServiceWorkerContainer` the app's `onServiceWorkerAlert` listens on) with a payload matching `parseTruckInboundMessage`'s contract (`{type:'alert', event:'TRUCK_INBOUND', id, route, who, when}`). A sanity-check listener added the same way on the same object *did* receive the dispatched event, confirming the dispatch mechanism itself works — but the app's own banner never appeared, and no console error was raised. I cannot tell from here whether this reflects a real gap in `TruckInboundHost`'s registration or is an artifact of dispatching outside a genuine service-worker-controlled page (this dev environment shows zero active `ServiceWorkerRegistration`s, i.e. no worker was ever installed here at all — `dev.sh`'s Vite dev server serves no `/sw.js`, per `pwa/serviceWorker.ts`'s own comment that this is "the normal state under `vite dev`"). Recommend a follow-up test against a production/Docker build with a real worker registered, or a Chrome DevTools Protocol-level push simulation.
- **Intermittent "Something went wrong. Tap to try again." on cold navigation into S2.2 and S2.3** (not on in-app client-side navigation, only on a fresh full page load / hard reload of a `/receive/.../stops/...` or `/donations/new` URL). Reproduced 3 times across the session, always recoverable with one tap on "Try again," and the underlying data (re-)loaded correctly every time. This coincided with `[vite] server connection lost. Polling for restart...` messages in the console around the same window, which points at the Vite dev server itself hiccuping under the rapid navigation this pass's testing method used, rather than a genuine app defect — but I can't fully rule out a real race (e.g. an initial fetch firing before auth/session context is ready on a true cold load). Flagging as an open question rather than a defect; worth a quick check against the production build with a plain hard-refresh (not the automation harness's rapid iframe-reload pattern).
- **Toast auto-dismiss timing and animation** (skeleton→content, toast fade): per this harness's stated limitation, only discrete screenshots were available; timing-sensitive behavior (e.g. whether the toast overlapping the keypad in Defect 3 actually blocks a tap, or is purely visual) could not be verified.
- **True concurrent multi-receiver behavior on one run** (S2.1b: "Multiple receivers can work the same run's different stops independently") — cannot hold two logged-in sessions in parallel per this harness's limitations; not tested.
- **Shared-device idle timeout ("Still here?" prompt):** not exercised — would require sitting idle for the timeout window, not attempted given the pass's scope and time budget.
